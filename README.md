# Складской учёт — версия 3

Приложение для упаковщиков: учёт упаковки и часов, расчёт зарплаты, чат, остатки упаковочных материалов, синхронизация каталога с Ozon.

## Как устроено

- `server.js` — сервер (Node.js + Express): вход и сессии, права доступа, хранилище данных, синхронизация с Ozon, ежедневные снимки.
- `lib/` — части сервера:
  - `build.js` — сборка интерфейса (см. ниже);
  - `auth.js` — пароли, сессии, защита от перебора;
  - `access.js` — кто что может читать и менять;
  - `patch.js` — применение изменений к данным (слияние одновременных правок).
- `src/` — исходники интерфейса:
  - `App.jsx` — ядро: состояние, загрузка данных и все действия (логика без разметки разделов);
  - `screens/` — разметка разделов, по файлу на раздел: `auth` (вход), `admin-overview`, `admin-journal`, `admin-employees`, `admin-products`, `admin-stock`, `admin-messages`, `admin-settings`, `employee-work`, `employee-stock`, `modals-packaging`, `modals-common`;
  - `ui/` — стили (`styles.jsx`) и мелкие общие элементы (`components.jsx`);
  - `lib/` — общие функции: `helpers.js` (упаковка, даты, тексты), `server.js` (обмен с сервером), `sound.js`;
  - `data/seed.js` — начальный каталог и цены для первого запуска;
  - `entry.jsx` — точка входа; `storage.js`, `kvdiff.js` — обмен данными с сервером; `qr.js` — построение QR-кода.
- `public/` — страница-обёртка, service worker, иконки.

## bundle.js собирать не нужно

Сервер **сам** собирает интерфейс из папки `src/` при каждом запуске (занимает пару секунд). На GitHub загружаются только исходники. В логах приложения при старте должна быть строка:

```
✅ Интерфейс собран за ... мс (сборка ...)
```

Если вместо неё `❌ Не удалось собрать интерфейс: ...` — в сообщении будет причина (чаще всего не установились пакеты при деплое). Сайт в этом случае показывает сообщение об ошибке; чтобы вернуть рабочую версию — выберите в настройках стенда предыдущий коммит и передеплойте.

Старый файл `public/bundle.js`, если он остался в репозитории, больше не используется — его можно удалить.

## Обновление приложения

1. Распаковать архив, перетащить его содержимое на страницу «Upload files» репозитория на GitHub (с главной страницы репозитория, папки — мышью).
2. В Timeweb: «Настройки» стенда → «Коммит» → выбрать самый свежий коммит → деплой.
3. В логах проверить две строки: `✅ Подключено к PostgreSQL` и `✅ Интерфейс собран`.

## Вход и безопасность

- Логин и пароль проверяет сервер. После входа в браузере хранится только ключ сессии (cookie, недоступная скриптам); сессия живёт 180 дней с последнего захода и переживает обновления приложения.
- Пароли и секретные слова хранятся в виде хеша с солью (scrypt). Учётные записи, созданные в старых версиях (SHA-256), продолжают работать и переводятся в новый формат при первом входе.
- Без входа сервер не отдаёт никакие данные. Сотрудник получает только свои записи, свои замеры, общий чат и свой личный чат; справочники (каталог, цены, остатки упаковки) — только на чтение, кроме остатков и привязок упаковки.
- Цена за штуку и почасовая ставка в записи сотрудника берутся из данных сервера, а не из запроса браузера.
- Ключи с префиксом `_` (ключи Ozon, сессии) через общий API недоступны никому.
- Ключи Ozon и QR-коды входа шифруются в базе (AES-256-GCM), если задана переменная окружения `APP_SECRET` (случайная строка от 16 символов). Ключ шифрования в базе не хранится. Если `APP_SECRET` потерять или изменить — ключи Ozon нужно будет ввести заново, а прежние QR-коды перестанут действовать (пароли это не затрагивает).
- Самостоятельную регистрацию можно закрыть: Настройки → Данные и безопасность.

## База данных (PostgreSQL)

Если задана переменная окружения `DATABASE_URL` (или `PGHOST`/`PGPORT`/`PGUSER`/`PGPASSWORD`/`PGDATABASE`) — данные хранятся в PostgreSQL. Если нет — во временной папке, и стираются при каждом деплое.

**Разделы приложения хранятся в таблицах, по строке на элемент:**

| Раздел | Таблица | Отдельные столбцы |
|---|---|---|
| Сотрудники | `pt_users` | `username`, `role` |
| Записи (упаковка и смены) | `pt_entries` | `employee_id`, `entry_date`, `type`, `sku`, `ts` |
| Замеры секундомера | `pt_timer_sessions` | `employee_id`, `entry_date`, `ts` |
| Чат | `pt_chat_messages` | `thread_id`, `sender_id`, `ts` |
| Объявления | `pt_messages` | `to_employee_id`, `ts` |
| Журнал входов | `pt_login_log` | `user_id`, `ts` |
| История цен | `pt_price_history` | `sku`, `ts` |
| Штрихкоды от сотрудников | `pt_custom_barcodes` | `sku`, `barcode` |
| Каталог | `pt_catalog` | `name` |
| Цены упаковки | `pt_packaging_options` | `sku` |
| Упаковочные материалы | `pt_packaging_materials` | `sku`, `name` |
| Заявка на закупку | `pt_packaging_purchase_request` | — |
| Фото товаров | `pt_product_images` | — |
| Привязка упаковки к товарам | `pt_product_packaging_links` | — |
| Скрытые уведомления | `pt_dismissed_inactive_notices` | — |

У каждой таблицы: `project` (имя проекта), `id` (ключ элемента), `pos` (порядок), `data` (элемент целиком, JSONB), `updated_at`. Пример запроса в pgAdmin — сумма упакованного по сотрудникам за октябрь:

```sql
SELECT employee_id, sum((data->>'qty')::numeric * (data->>'unitPrice')::numeric) AS сумма
FROM pt_entries
WHERE project = 'packer-tracker' AND type = 'piece' AND entry_date BETWEEN '2026-10-01' AND '2026-10-31'
  AND data->>'deletedAt' IS NULL
GROUP BY employee_id;
```

Настройки, ежедневные снимки и служебные ключи (сессии, ключи Ozon) остаются в общей таблице `kv_store`.

**Загрузка по частям.** Приложение не скачивает записи и чат целиком:
- записи — `GET /api/entries?from=ГГГГ-ММ-ДД&to=ГГГГ-ММ-ДД` (при открытии — с первого числа месяца перед текущим расчётным периодом; более ранние догружаются, когда в фильтре выбирают раннюю дату, или кнопками «Ещё 3 месяца» / «Все записи»);
- чат — `GET /api/chat?fromTs=...` (последние 30 дней, более ранние — по кнопке); звук голосовых в списке не передаётся и запрашивается отдельно при нажатии (`GET /api/chat/audio/:id`);
- таблицы журнала и истории показывают по 100 строк с кнопкой «Показать ещё».

**Как включаются таблицы.** При каждом запуске сервер создаёт недостающие таблицы и проводит самопроверку на отдельной служебной таблице. При первом запуске переносит все разделы из `kv_store` одной транзакцией и сверяет каждый с оригиналом. Если самопроверка или сверка не прошли — таблицы не включаются, приложение работает по-старому, данные не меняются (в логах будет строка с `❌` и причиной). Старые значения в `kv_store` после переноса не удаляются, но и не обновляются.

**Важно про откат.** После переноса откатываться на версию до 3.3.0 не стоит: старая версия будет читать устаревшие данные из `kv_store`, а всё записанное ею потом не попадёт в таблицы.

Одну базу можно использовать для нескольких проектов: каждому задаётся свой `PROJECT_NAME` (по умолчанию `packer-tracker`).

## Каталог товаров — из приложения «Мой склад»

Настройки → «Каталог товаров» → адрес «Моего склада» и ключ доступа (`msa_…`, создаётся в «Моём складе»: Настройки → «Аналитика МП» → ключ с названием «Складской учёт»). Логика — в `lib/moysklad.js`.

- Читается `GET <адрес>/api/analytics/v1/products` (заголовок `X-Api-Key`), постранично.
- Раз в 30 минут сервер сам забирает изменившиеся товары; полная сверка — кнопкой.
- Название, штрихкоды и фото берутся из «Моего склада». Удалённый там товар здесь помечается (сотрудникам не показывается, записи сохраняются). При смене артикула записи, цены, фото и привязка упаковки переносятся на новый артикул.
- История синхронизаций с отменой (смена артикула не отменяется).
- Пока «Мой склад» подключён, синхронизация с Ozon отключена. Ключ хранится зашифрованным (при заданном `APP_SECRET`).

## Доступ для других приложений (внешний API)

Другие ваши приложения читают данные по ключу доступа (Настройки → «Доступ для других приложений»). Только чтение, заголовок `Authorization: Bearer <ключ>`:

- `GET /api/ext/v1/packaging/materials` — остатки упаковки;
- `GET /api/ext/v1/packaging/moves?since=<отметка>&limit=<до 1000>` — журнал движений упаковки (приход `in`, списание `out`, инвентаризация `set`, списание при упаковке товара `pack`, создание `new`, удаление `delete`); «только новое» — по `nextSince` из прошлого ответа;
- `GET /api/ext/v1/packaging/links` — привязка упаковки к товарам;
- `GET /api/ext/v1/packaging/rates` — расценки за упаковку: основная (`rate`), все варианты (`variants`), фактическая средняя за 30 дней (`avgRate30d`), статус (`rateStatus`: `set` / `no_work` / `not_set`) и признак `noLabor` (работа не нужна — расценка 0 у товара с отметкой «упаковка не нужна»);
- `GET /api/ext/v1/payroll/hourly?from=ГГГГ-ММ-ДД&to=ГГГГ-ММ-ДД` — почасовая оплата упаковщиков по дням: `amount`, `pendingAmount` (по ещё не подтверждённым сменам), `hours`, `employees`.

Журнал движений (`pt_packaging_moves`) пишет сам сервер в одной транзакции с изменением остатка; изменить или очистить его запросом нельзя.

## Резервные копии

- Сервер сам раз в сутки делает снимок данных и хранит последние 14 (Настройки → Данные и безопасность → список снимков).
- «Скачать бэкап (JSON)» — полная копия: сотрудники (с хешами паролей), записи, цены, каталог, фото, упаковка, объявления, чат, настройки.
